# Axelor Framework Architecture

## Overview

Axelor is a Java-based open-source ERP framework using a **Model-Driven** approach (MDD - Model Driven Development). Java entity code is **automatically generated** from XML definitions.

## Key Principle: Model-Driven Development (MDD)

### Development Flow

1. **Define the model** (XML domain file)
   ```xml
   <entity name="Customer">
     <string name="code" />
     <string name="fullName" />
   </entity>
   ```

2. **Generate the code** (Gradle command)
   ```bash
   ./gradlew generateCode
   ```

3. **Java code automatically generated** in `build/src-gen/`
   ```java
   @Entity
   public class Customer extends AuditableModel {
     @Column(name = "code")
     private String code;

     @Column(name = "full_name")
     private String fullName;

     // Getters, setters, hashCode, equals...
   }
   ```

4. **Database automatically created** by Hibernate (JPA)

### ⚠️ Golden Rule

**NEVER modify generated code in `build/src-gen/`** as it will be overwritten on next generation.

All modifications must be made in the XML source files.

## Main Technologies

### Backend
- **Java 11+**: Main language
- **Gradle**: Build tool
- **JPA/Hibernate**: ORM (Object-Relational Mapping)
- **Guice**: Dependency Injection
- **PostgreSQL**: Database (recommended)

### Frontend
- **HTML5 + AngularJS**: UI framework
- **WebSocket**: Real-time communication
- **REST API**: Client-server communication

## Dependency Injection (Guice)

Axelor uses **Google Guice** for dependency injection.

### Standard Pattern

```java
public class CustomerServiceImpl implements CustomerService {

  @Inject
  private CustomerRepository customerRepository;

  @Inject
  private OrderService orderService;

  @Override
  public Customer create(Customer customer) {
    // Implementation
  }
}
```

### ⚠️ Important Rules

- **@Inject**: Inject dependencies (no `new`)
- **Interfaces**: Always code against interfaces
- **Stateless**: Services must not have state
- **Singleton**: Services are singletons by default

## Transactions

Transactions are managed with **@Transactional**.

### Standard Pattern

```java
public class CustomerServiceImpl implements CustomerService {

  @Transactional
  public Customer create(Customer customer) {
    // This method runs in a transaction
    // Automatic commit if no exception
    // Automatic rollback if exception
    return customerRepository.save(customer);
  }

  @Transactional(rollbackOn = {AxelorException.class})
  public void complexOperation() throws AxelorException {
    // ...
  }
}
```

### ⚠️ Important Rules

- **@Transactional** on public methods only
- **No @Transactional** in controllers (delegate to services)
- **Exceptions**: RuntimeException triggers automatic rollback
- **Checked exceptions**: Specify `rollbackOn` if rollback needed

## Security and Permissions

### Security Levels

1. **Groups and roles**: Define who has access
2. **Object Access**: CRUD permissions per model
3. **Field Access**: Permissions per field
4. **Record Rules**: Data filters (e.g., see only own records)

### Configuration Example

```xml
<object-views xmlns="http://axelor.com/xml/ns/object-views">

  <!-- Permission on Customer model -->
  <access-rule model="com.axelor.apps.mymodule.db.Customer"
               groups="mymodule.user"
               perm="read,create,write"/>

  <access-rule model="com.axelor.apps.mymodule.db.Customer"
               groups="mymodule.manager"
               perm="read,create,write,remove"/>

  <!-- Permission on specific field -->
  <field-access model="com.axelor.apps.mymodule.db.Customer"
                field="creditLimit"
                groups="mymodule.manager"
                perm="read,write"/>
</object-views>
```

## Typical Development Cycle

### 1. Create/Modify XML domains
```xml
<!-- domains/Customer.xml -->
<entity name="Customer">
  <string name="code" required="true" unique="true" />
  <string name="fullName" required="true" />
  <string name="email" />
</entity>
```

### 2. Generate code
```bash
./gradlew generateCode
```

### 3. Create XML views
```xml
<!-- views/Customer.xml -->
<form name="customer-form" model="com.axelor.apps.mymodule.db.Customer">
  <panel name="main">
    <field name="code" />
    <field name="fullName" />
    <field name="email" />
  </panel>
</form>
```

### 4. Implement services (if business logic)
```java
public class CustomerServiceImpl implements CustomerService {

  @Inject
  private CustomerRepository customerRepository;

  @Transactional
  public Customer create(Customer customer) {
    // Custom business logic
    customer.setCode(generateCode());
    return customerRepository.save(customer);
  }
}
```

### 5. Create controllers (if custom actions)
```java
public class CustomerController {

  // NO @Inject in controllers - use Beans.get()

  public void validate(ActionRequest request, ActionResponse response) {
    Customer customer = request.getContext().asType(Customer.class);
    customer = Beans.get(CustomerService.class).validate(customer);
    response.setReload(true);
  }
}
```

### 6. Compile and run
```bash
./gradlew build
./gradlew run
```

### 7. Access application
```
http://localhost:8080
```

## Architectural Best Practices

### ✅ DO

- **Separate responsibilities**: Domain → Repository → Service → Controller
- **Code against interfaces**: No direct coupling to implementations
- **Stateless services**: No state in services
- **Explicit transactions**: @Transactional on methods that modify data
- **Business validation in services**: Not in controllers
- **Appropriate logs**: DEBUG for details, INFO for workflow, ERROR for errors
- **Unit tests**: Cover business logic

### ❌ DON'T

- **Business logic in domains**: Entities = data only
- **Business logic in controllers**: Controllers = orchestration only
- **Modify generated code**: Always modify XML sources
- **Transactions in controllers**: Delegate to services
- **Queries in controllers**: Go through repositories/services
- **State in services**: Services must be thread-safe
- **Tight coupling**: Use dependency injection
