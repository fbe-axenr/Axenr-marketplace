# EPIC Generation Workflow

This document describes the detailed step-by-step process for generating EPICs and User Stories from refined specifications. This workflow is used by the agile-agent agent.

---

## Overview

The EPIC generation process follows 5 main steps:

1. **Analyze Specification** - Understand scope and identify components
2. **EPIC Decomposition** - Propose EPIC structure
3. **Generate User Stories** - Create detailed US for each EPIC
4. **Define EPIC Acceptance Tests** - Create end-to-end scenarios
5. **Add Definition of Done** - Define completion criteria

---

## Step 1: Analyze Specification

### Objective
Read the refined specification document completely and extract all key information needed for EPIC/US decomposition.

### Input
- Refined specification document from `{output_directory}/detailed-specifications.md`
- Generated by requirements-refiner agent
- Markdown format with structured sections

### Process

1. **Read specification completely**
   - Don't skip sections
   - Pay attention to cross-cutting aspects
   - Note ambiguities or missing information

2. **List all business entities**
   - Extract from "Business Entities" section
   - Note complexity (number of fields, relationships)
   - Identify core vs. supporting entities

   Example extraction:
   ```
   Entities identified:
   - Message (Complex: 15 fields, 4 relationships)
   - EmailAccount (Medium: 8 fields, 2 relationships)
   - MailFolder (Simple: 5 fields, 1 relationship)
   - OfficeMail (Bridge: 3 fields, 2 relationships)
   ```

3. **List all features**
   - Extract from "Features" section
   - Note scope and dependencies
   - Categorize by type (CRUD, workflow, integration, etc.)

   Example extraction:
   ```
   Features identified:
   - Email viewing (grid + form views)
   - Email status management (read/unread)
   - Email folder navigation
   - Manual calendar sync
   - Search and filtering
   ```

4. **Identify natural boundaries for EPICs**
   - Group related entities and features
   - Consider dependencies
   - Aim for EPICs of 3-10 days each

   Example boundaries:
   ```
   Potential EPICs:
   1. Message Entity Foundation (entities + views)
   2. Email Status Management (workflow)
   3. Folder Navigation (tree view + filtering)
   4. Calendar Synchronization (integration)
   ```

5. **Note cross-cutting concerns**
   - Security and permissions
   - Internationalization
   - Performance requirements
   - Audit/logging requirements

   Example cross-cutting:
   ```
   Cross-cutting aspects:
   - Security: Domain-level filtering by user email
   - I18n: French and English required
   - Performance: Grid must handle 1000+ emails
   - Audit: Log all status changes
   ```

### Output

Document your analysis in this format:

```markdown
## Specification Analysis

### Business Entities (X total)
- **Entity1Name** (Complexity: S/M/L): [brief description]
- **Entity2Name** (Complexity: S/M/L): [brief description]
[...]

### Features (Y total)
- **Feature1**: [brief description, scope]
- **Feature2**: [brief description, scope]
[...]

### Natural EPIC Boundaries
Based on entity groupings and feature domains:
1. [EPIC candidate 1]: [entities/features included]
2. [EPIC candidate 2]: [entities/features included]
[...]

### Cross-Cutting Concerns
- Security: [requirements]
- I18n: [languages]
- Performance: [constraints]
- Other: [aspects]
```

## Step 2: EPIC Decomposition

### Objective
Propose a structured decomposition into EPICs and get validation before generating detailed User Stories.

### Decomposition Strategies

Choose one or combine multiple strategies based on the specification:

#### Strategy A: By Business Entity

Use when:
- Specification has 3-8 clearly defined entities
- Each entity is complex enough (10+ fields, multiple relationships)
- Entities have independent business value

Pattern:
- One EPIC per main entity
- Include domain, views, and basic logic in same EPIC
- Group supporting entities with their parent

Example:
```
EPIC 1: Customer Management Entity
  - Customer domain, grid, form, menu
  - Customer address sub-entity
  - Customer contact sub-entity

EPIC 2: Product Catalog Entity
  - Product domain, grid, form, menu
  - Product category taxonomy
  - Product pricing
```

#### Strategy B: By Feature Domain

Use when:
- Specification describes distinct feature areas
- Features span multiple entities
- Features have clear business domain boundaries

Pattern:
- Group related features into EPICs
- Include all entities needed for the feature
- Separate foundation from advanced features

Example:
```
EPIC 1: Email Viewing Foundation
  - Message entity
  - Grid and form views
  - Basic display functionality

EPIC 2: Email Management Features
  - Status management (read/unread)
  - Folder operations (move, delete)
  - Search and filtering
```

#### Strategy C: By Technical Layer

Use when:
- Large specification with many entities
- Clear separation between data model, UI, and logic
- Team wants to work in phases (model first, then UI, then logic)

Pattern:
- EPIC 1: Data model (all domains)
- EPIC 2: UI layer (all views)
- EPIC 3: Business logic (all services)

**Warning**: This strategy can delay business value delivery. Use only when justified.

#### Strategy D: By Priority/Phase

Use when:
- Specification has clear priority levels
- MVP vs. future phases defined
- Incremental delivery required

Pattern:
- EPIC 1-3: High priority (MVP) features
- EPIC 4-6: Medium priority (Phase 2)
- EPIC 7+: Low priority (future enhancements)

### Proposed EPIC Structure Format

```markdown
## Proposed EPIC Structure

### EPIC 1: [Clear Business-Oriented Name]
- **Scope**: [What's included - entities and features]
- **Entities**: [Entity1, Entity2, Entity3]
- **Features**: [Feature1, Feature2]
- **Estimated effort**: [X person-days]
- **Priority**: [High/Medium/Low]
- **Rationale**: [Why these are grouped together]

### EPIC 2: [Name]
[same structure]

### EPIC 3: [Name]
[same structure]

---

**Total EPICs**: X
**Total Estimated Effort**: Y person-days
**Estimated Project Duration**: Z weeks (assuming N developers)
```

### Validation Checkpoint

**IMPORTANT**: After proposing EPIC structure, ASK FOR VALIDATION before proceeding.

Present to the user:
```
I have analyzed the specification and propose the following EPIC structure:

[Your proposed EPIC structure]

Does this decomposition align with your priorities and delivery plan?
Would you like to:
- Approve this structure and proceed with User Story generation
- Adjust EPIC boundaries (merge/split/reorder)
- Change priority levels
- Discuss alternative decomposition strategies
```

Do not proceed to Step 3 until you receive approval or adjustment feedback.

## Step 3: Generate User Stories

### Objective
For each approved EPIC, generate detailed User Stories following Axelor patterns.

### Process Per EPIC

#### 3.1 Determine US Sequence

Based on EPIC type, determine the logical order for User Stories:

**For Entity-Based EPICs**, use this sequence:
1. Domain creation (foundational)
2. Grid view (list display)
3. Form view (detail/editing)
4. Menu integration (navigation)
5. Business logic (features)

**For Feature-Based EPICs**, use this sequence:
1. Service layer (business logic foundation)
2. UI components (views, actions, buttons)
3. Integration points (external systems, workflows)
4. Permissions (security configuration)

**For Workflow EPICs**, use this sequence:
1. Workflow service (state machine logic)
2. State-dependent UI (buttons, visibility)
3. Notifications (email, alerts)
4. Audit/logging (compliance)

#### 3.2 Use Appropriate Patterns

Refer to pattern documents for each US type:

- **Entity CRUD**: See [Entity-Based US Patterns](../examples/entity-based-us-patterns.md)
- **Security**: See [Special Case US Patterns](../examples/special-case-us-patterns.md) - Security section
- **Import/Export**: See [Special Case US Patterns](../examples/special-case-us-patterns.md) - Import/Export section
- **Workflows**: See [Special Case US Patterns](../examples/special-case-us-patterns.md) - Workflow section
- **Dashboards**: See [Special Case US Patterns](../examples/special-case-us-patterns.md) - Dashboard section

#### 3.3 Apply Estimation

For each User Story, estimate complexity using the skill:

- Use `@skills/epic-estimator` for standardized estimation
- Input: User story description, component types
- Output: Complexity (S/M/L/XL) + effort estimation

**If XL complexity**: Break down into smaller stories immediately.

#### 3.4 Identify Dependencies

For each User Story, identify dependencies:

- Use `@skills/us-dependency-mapper` for systematic dependency mapping
- Input: List of User Stories with technical details
- Output: Dependency graph and blocking relationships

Document dependencies in each US:
```textile
h4. Dependencies

* Depends on: US-001 (Domain must exist before views)
* Depends on: US-005 (Related entity needed for relationship)
* Blocks: US-010 (This US must be completed first)
```

#### 3.5 Write Complete User Stories

For each US, write all sections following the template:

- **Title**: Action-oriented, clear
- **User story statement**: As a... I want... So that...
- **Acceptance Criteria**: Specific, testable, checkbox format
- **Technical Details**: Axelor-specific (domains, views, services)
- **Estimation**: Use skill output
- **Dependencies**: Use skill output

**Quality check with**: `@skills/us-quality-validator`

## Step 4: Define EPIC Acceptance Tests

### Objective
Create end-to-end acceptance scenarios that validate the complete EPIC delivers business value.

### Process

1. **Identify happy path scenario**
   - Most common user workflow
   - Uses multiple User Stories together
   - Delivers complete business value

   Example:
   ```
   Scenario: Sales rep views and manages customer email
   1. User opens Inbox
   2. User filters emails by customer name
   3. User opens email to read
   4. User marks email as unread for follow-up
   5. User closes email
   6. Email appears in bold in grid
   ```

2. **Identify alternative flows**
   - Valid alternative paths
   - Error handling scenarios
   - Recovery procedures

   Example:
   ```
   Scenario: Bulk marking emails with permission error
   1. User selects 10 emails
   2. User clicks "Mark as Read"
   3. 8 succeed, 2 fail (permission denied)
   4. User sees partial success message
   5. Error details available for failed emails
   ```

3. **Identify edge cases**
   - Boundary conditions
   - Unusual data
   - Rare situations

   Example:
   ```
   Scenario: Email with very large attachment
   1. User opens email with 25MB attachment
   2. Attachment preview disabled (too large)
   3. Download button available
   4. Download initiates with progress bar
   ```

4. **Write scenarios** using template from [EPIC Acceptance Tests Template](../templates/epic-acceptance-tests.md)

## Step 5: Add Definition of Done

### Objective
Define clear completion criteria for the EPIC.

### Standard DoD Checklist

Include all applicable items:

```textile
h2. Definition of Done (DoD)

For this EPIC to be considered complete:

* [ ] All User Stories in DONE status
* [ ] Domain XML files created and generateCode successful
* [ ] All views created and functional
* [ ] Business logic implemented and unit tested
* [ ] Integration tests written and passing
* [ ] Code reviewed and compliant with Axelor conventions
* [ ] Technical documentation updated (JavaDoc, inline comments)
* [ ] i18n keys defined for all languages
* [ ] Database migration script created (if needed)
* [ ] Deployed to test environment
* [ ] Functional validation by Product Owner completed
* [ ] No critical or blocking bugs remaining
```

### Customize Per EPIC

Add specific criteria based on EPIC type:

**For Security-focused EPICs**, add:
```textile
* [ ] Security audit passed
* [ ] Penetration testing completed
* [ ] Permission matrix validated for all roles
```

**For Integration EPICs**, add:
```textile
* [ ] External system integration tested
* [ ] Error handling and retry logic verified
* [ ] API rate limiting respected
* [ ] Monitoring and alerting configured
```

**For Performance-critical EPICs**, add:
```textile
* [ ] Performance benchmarks met (e.g., grid loads < 2s for 1000 records)
* [ ] Load testing completed (X concurrent users)
* [ ] Database indexes optimized
```

---

## Final Output

After completing all 5 steps, you will have generated:

1. **Complete EPIC/US breakdown** with:
   - All EPICs with objectives and acceptance criteria
   - All User Stories with detailed AC and technical specs
   - Dependencies mapped between stories
   - Realistic estimations
   - Acceptance test scenarios
   - Definition of Done

2. **Summary information**:
   - Total EPICs count
   - Total US count
   - Total effort estimation
   - Development roadmap suggestion

3. **Ready for next stage**:
   - Input for architect agent
   - Backlog for sprint planning
   - Redmine import (if using Textile format)
